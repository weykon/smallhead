# TUI 常驻服务管理面板：设计与运行机制

状态：基础实现已纳入，2026-10-15（feat/monad-slices-1-4）；审核修复见下文。本文仍保留后续设计建议，不代表所有建议均已交付。

## 审核后的实际行为

- Agent 使用 `process_control(action=service_update_description, name, description)` 更新自由文本说明，独立保存更新时间；巡检只提交健康字段，不覆盖说明。
- `service_ensure(name)` 优先使用已登记配置。普通项目服务可同时省略 health_url/identity，仅确认受管进程运行，界面显示「运行中」，不声称身份验证成功。此类服务重启后仍是 Unknown，不自动认领旧进程。
- 停止先持久化 desired_running=false 并推进控制版本，再等待进程退出；只读检查不推进控制版本。检查提交在同一个写锁内核对版本，已遗忘服务不重新插回。取消等待者不丢失启动/停止收尾责任。
- TUI 启动时持有健康调度器，退出时关闭；启动中的服务由 ensure 检查，周期检查不重复派发。每服务检查串行，所有探测共用并发预算。
- 服务页支持 ↑↓ 选中、Enter 进入详情、Esc 返回列表、PgUp/PgDn 滚动、Tab/Shift+Tab 切详情标签，以及 s/x/r/d 启动/停止/检查/清除登记。窄屏切换列表和详情，待答 Choice 只在聊天页接管按键。
- 事件在启动时有界加载，随后由广播更新缓存；渲染不读取磁盘，最近事件优先。输出按 500ms 间隔刷新。完整操作区焦点循环、通用配置编辑和自动重启仍属于后续工作。

下文示例中的 `service_update_info` 是设计期名称，实际接口统一使用 `service_update_description`；文档中的其他建议以本节实际行为为准。

## 1. 用户需求与边界

用户需要一个可以直接查看和管理常驻服务的 TUI 面板：哪些服务可用、谁启动的、当前是否健康、出了什么问题，以及如何启动、停止、查看日志。

已确认方向：

- 提供面向用户的服务信息与管理界面，不能只有原始 JSON 或聊天中的工具返回值。
- 顶部只保留一排带快捷键的入口，不重复列出同一组页签。
- 本轮先讨论设计，再由另一开发 Agent 实施服务面板。
- 不增加用户可见的 Session 管理，不以 World/Scope/Checkpoint/Lens 新设计作为前置条件。
- 不调整当前权限策略；服务管理继续使用现有执行边界。
- 2026-10-15 已确认：同时容纳基础服务和 Agent 建立的项目服务。用途、已启动/可访问/身份验证等用户可见情况由 Agent 写自然语言说明，不新增固定展示字段或三项检查卡片。
- 提供 Agent 更新说明的工具入口，提示词指导填写；底层启停、执行 ID 和管理归属仍使用管理器事实。

首版建议聚焦本机服务。Agent-Reach 当前按次调用 CLI，不因为它是工具就登记为常驻服务。只有真正长时间运行、有服务身份的进程才进入此页。

## 2. 当前代码事实

| 模块 | 已有能力 | 本次设计需要补足 |
|---|---|---|
| `smallhead-process/src/service.rs` | `ServiceSpec/ServiceRecord`；ensure/inspect/stop/forget；同名 ensure 协调；身份健康检查；services.json | 连续观测信息、结构化事件、并发状态提交约束 |
| `smallhead-core/src/execution.rs` | process_control 服务操作；Laya/Qwen 预设；支持传自定义 ServiceSpec | 按已登记配置再次启动自定义服务，避免仅按预设名解析 |
| `smallhead-tui/src/processes.rs` | 进程页内服务区；选择、启动、停止、inspect、展开详情；启动进度任务 | 独立服务页、稳定选择、统一操作状态与可读详情 |
| `smallhead-tui/src/app.rs` | Ctrl+P/F3 进程页；服务命令；键盘和鼠标分发 | 服务页路由和焦点管理 |
| `smallhead-tui/src/render.rs` | 顶部入口、点击命中区、聊天/日志/进程渲染 | 服务入口与响应式布局 |

现有服务状态是 Starting、Ready、Degraded、Stopped、Failed、Unknown。`list()` 返回快照，`inspect()` 才主动检查健康。没有持续 supervisor、自动重启、依赖传播。

服务登记已经持久化，但不等于进程跨应用托管。Smallhead 正常退出时清理自己启动的服务；外部服务不由 Smallhead 停止。异常退出后不凭旧 PID 接管或发送信号。

当前健康协议仅支持 loopback HTTP 和预期 JSON 字段，单次 HTTP 检查超时 800ms；启动就绪等待最多 120s。这是现状。为支持普通项目服务，需补足无需身份 JSON 的受管启动方式，仍经 ProcessManager 创建并持有执行；进程存活不伪装成健康协议已验证。具体内部状态表示由开发实现确定，不扩张用户可见的语义字段。

## 3. 建议界面

建议新增独立「服务」页，与「聊天」「日志」「进程」并列；服务不再作为进程页中另一套可操作的完整列表。进程页仍显示服务对应的底层执行，可跳回服务详情。

建议入口：`Ctrl+S` 打开服务页，`Ctrl+P / F3` 保持打开进程页。Ctrl+S 在部分终端会被流控拦截，因此必须同时提供 `/services` 命令和鼠标入口；现有 `/service ensure|inspect|stop|forget name` 继续兼容。快捷键最终待讨论，不占用现有 F4-F8 的进程操作。

宽屏示意（具体列宽按实际 Unicode 显示宽度计算）：

```text
[聊天 F1] [日志 F2] [进程 Ctrl+P] [服务 Ctrl+S]

服务                              qwen
名称       状态       管理方式     状态：就绪     管理方式：本应用管理
laya       未启动     预设         期望：运行     最近检查：2 秒前
> qwen     就绪       本应用管理   健康地址：http://127.0.0.1:3032/health
preview    健康异常   外部         工作目录：/path/to/project
                                  启动命令：sh experiments/.../start.sh
                                  最近结果：健康身份验证通过

                                  [概览] [输出] [事件]
                                  ...当前详情或分页日志...

↑↓ 选择 · Tab 焦点 · Enter 详情 · s 启动 · x 停止 · r 检查 · Esc 返回
```

### 列表

- 展示名称、状态、管理方式；宽度充足再展示最近检查时间和简短异常原因。
- 预设 Laya/Qwen 即使未登记也可发现，显示「未启动」，不是伪造 Stopped 运行记录。
- 已登记自定义服务与预设合并显示，同名优先使用已登记配置。
- 用服务名保持选择，不用行号。刷新、删除和排序不能把操作目标悄悄换成另一服务。
- 状态同时用文字和颜色表示；错误不能只靠红色。

### 详情

概览优先展示名称、管理器当前状态、管理方式，以及 Agent 填写的自由文本说明和更新时间。用途、项目、访问地址、已启动/可访问/身份检查情况可以写在同一段说明中，不设置固定字段。没有说明时显示「暂无服务说明」，不据此判断服务不可用。

启动命令、工作目录、执行 ID、日志目录和已有健康配置放可展开的技术详情。上方示意图中的健康字段是技术详情内容，首屏以 Agent 说明为主。

PID 只在当前管理器确认仍持有该执行时显示为当前 PID；旧记录只能作为历史信息。外部服务没有执行日志时明确显示「未由本应用采集」，不伪造空日志。

输出页复用 ProcessManager 分页读取 stdout/stderr；事件页显示状态变化和用户/Agent 的管理操作。显示是否截断及是否自动跟随，不能每帧加载完整日志。详情中提供复制日志目录和跳到对应进程的动作。

命令和错误文本需要按现有诊断脱敏规则展示；不新增环境变量值、令牌或完整响应体的无过滤输出。

### 窄屏与键盘

- 宽度不足时用「列表 → Enter 打开详情 → Esc 返回列表」布局，避免横向挤压。
- 页签只有一份；无法完整容纳时缩短标签或分行，点击区域必须与可见字符一致，不能出现半截可点击操作。
- Tab/Shift+Tab 在列表、详情、操作区间移动焦点；↑↓ 作用于当前焦点；PgUp/PgDn 滚动详情；End 恢复日志跟随。
- 操作区用方向键选中动作、Enter 执行，字母快捷键只是可选加速方式，不要求用户背键位。
- 输入框和表单获得焦点时，普通字母进入输入内容，不触发服务操作。
- 后台出现 Choice 卡片不能抢走服务页的方向键和 Esc；用可见提示告知聊天页有待回复问题。
- Esc 按层返回：关闭操作菜单/详情，再返回进入服务页前的页面；不把 Esc 当停止服务。

## 4. 管理动作与状态规则

| 动作 | 行为 | 不可用情况 |
|---|---|---|
| 启动/确保就绪 | 预设构建配置；已登记服务复用原配置；调用 ensure | 同名操作正在进行；Unknown 未完成身份确认 |
| 检查 | 立即探测并更新健康观察；Unknown 使用专门的身份核对流程 | 同名探测已在进行时合并请求 |
| 停止 | 调用 stop，等待实际退出；展示「正在停止」 | 外部服务；历史身份未知；没有可停止的当前受管执行 |
| 查看输出/事件 | 读取关联执行日志或服务事件 | 没有采集来源时显示原因 |
| 清除登记 | 调用 forget；成功后移除登记 | 不满足已有 forget 条件，或仍有活跃受管执行 |

「清除登记」不表示卸载软件、删除文件、删除日志或停止服务。UI 在动作旁明确这个含义；无需新增统一权限审批流程。

已有 Ready 外部服务允许检查与复用，不允许停止。现有 TUI 对外部服务连 ensure 也禁止的逻辑需要调整：不能把「没有停止权」误当作「不能复用」。

首版不提供一键重启：停止未确认时不能继续启动第二个实例。后续增加重启必须是可查询的管理器操作，有明确停止结果和新的执行 ID。

编辑配置、任意新增服务暂列第二阶段。首版至少支持预设的启动，以及 Agent 已登记自定义服务的查询、再次启动和停止。不能只把 Laya/Qwen 两个名字写死在 UI 操作中。

## 5. 数据与机制

### 唯一事实来源

ServiceManager 持有服务登记、状态、期望和操作结果，ProcessManager 持有真实进程事实。TUI 只持有视图快照、选中名称、焦点、分页偏移和未完成操作 ID。

用户动作和 Agent 的 process_control 调用走同一管理器接口。鼠标、键盘、slash 命令不能各写一套启动和停止逻辑。UI 不直接 spawn/kill，也不直接编辑 services.json。

### Agent 服务说明入口（已确认方向）

建议在现有 process_control 增加 `service_update_info`，只有定位用的 `name` 和展示用的 `text`。具体命名可随现有 API 风格调整。首次登记可接收同一份可选说明，更新说明不要求重新启动。

```json
{
  "action": "service_update_info",
  "name": "site-preview",
  "text": "my-site 的开发预览服务，地址 http://localhost:3000。进程已启动，刚才请求首页返回 200；未配置独立身份检查。用于这次页面修改的预览。"
}
```

文本整体保存、整体替换，允许多行；不解析里面的地址、状态或标签，不要求固定模板。建议上限 4000 字符，超限返回错误；空文本可清空说明。更新时间由运行时生成，随说明一起保存进服务登记，旧数据默认无说明。未知服务名返回错误，不能通过更新文字凭空建立有停止权的服务。

说明是展示元数据，不参与 ServiceSpec 配置相等性判断，避免改文案触发同名配置冲突。更新时只修改说明和时间，不能覆盖并发 stop/inspect 的结果；巡检也不能覆盖最新说明。

Agent 不能通过说明修改 PID、external、desired_running 或生命周期状态。文本不自动转为管理操作、就绪判据或复用凭证。例如写「身份验证通过」不会赋予停止外部进程的能力。

TUI 标出「服务说明 · 更新时间」，旁边保留真实运行状态。进程后来退出时立即显示退出事实，不等待 Agent 重写文字；历史说明可继续展示，但不能冒充新的检查结果。说明更新只刷新面板，工具返回简短成功结果，不把整段文字刷进聊天。

### 建议注入的提示词

以下内容供开发 Agent 接入工具说明和运行时提示词：

> 为用户启动或维护常驻服务时，登记到服务管理器，并使用 service_update_info 更新服务面板的说明。说明写给用户阅读：简要说明服务做什么、与哪个项目有关、怎样访问，以及你实际检查到了什么。自然描述进程是否启动、地址是否可访问、是否验证了服务身份；没有检查的内容说明尚未检查，不需要凑齐固定字段。启动成功、失败、检查得到新结果或用途改变后更新说明。只创建进程不能声称页面已可用，HTTP 能访问也不等于身份已验证。仅修改说明时不要重启服务。不要写入完整日志、令牌或环境变量值。

不为周期刷新额外调用模型。Agent 在相关任务中更新文字，用户直接停止时由管理器更新事实状态即可。

### 内部实现组织

不要求新增 ServiceObservation 或完整的服务语义 schema。复用现有记录和事件，仅在并发管理确实需要时补操作 ID、运行版本等内部字段，保留在现有 crate。不要把 Agent 文本重新拆成结构化指标。

时间字段采用可持久化的 UTC 时间；UI 转为本地显示。计时使用单调时钟。旧登记缺少新增字段时通过 serde 默认值兼容读取。

### 健康刷新

建议服务管理器统一调度，而非渲染函数或每个 TUI 页面各自轮询：

- 对期望运行的服务每 5 秒检查一次；Stopped 不轮询；Unknown 走恢复核对，不能当普通 Ready 探测。
- 同一个服务最多一个探测请求，全局最多两个；一次请求结束才安排下一次，不堆积过期定时任务。
- 手动检查复用在途探测；进入页面立即取快照并触发一次必要刷新。
- 页面关闭后检查仍继续；应用关闭时取消调度并等待其收尾，再关闭进程管理器。
- 首版沿用现有单次失败即 Degraded 的语义，同时保留失败时间/原因；不要为引入连续失败阈值另造隐含状态。
- 进程实际退出优先于 HTTP 返回；不得因为同端口另一进程返回成功就把已退出的受管实例改为 Ready。
- 每次检查可更新内存观察；只在状态/配置/意图改变时持久化登记，避免每 5 秒重复重写 services.json。
- 相同失败合并计数，状态转移只发一次事件；周期健康结果不反复写入聊天。

5 秒、并发 2 是初始建议，实施时集中为配置常量。启动中的 readiness 检查复用现有启动流程，不同时叠加巡检。

### 并发与生命周期

当前 ensure 的同名 gate 不足以覆盖所有 inspect/stop/forget 交错；扩展 UI 前需要补齐管理器约束：

- 每个服务有版本号/运行代次。探测前取快照，异步 I/O 后只在版本仍匹配时提交结果。
- stop 先记录 desired_running=false 并使旧启动/探测结果失效；等待中的 ensure 必须观察停止意图，不得晚到后重新设成 Ready。
- forget 后的旧探测结果直接丢弃，不能 unwrap 已不存在的记录或重新插回已删除服务。
- 同名重复启动合并或返回当前操作，不创建多个实例；不同服务可独立操作。
- 不能为了串行化而让 stop 在 120 秒启动等待之后才生效。慢 I/O 不持有全局锁；per-service 状态协调与等待过程分离。
- 前端显示「正在启动/停止/检查」来自操作状态；不能因为请求已发送就显示成功。尤其现有 stop 提前写 Stopped 的窗口需要修正或由权威操作状态覆盖。
- 后台任务由管理器持有并追踪；关闭页面不取消启动操作，应用 shutdown 才统一收尾。

### 恢复和持久化

沿用 services.json 的原子替换和 ProcessManager 的目录锁，不新增用户 Session 或通用 checkpoint 系统。

重启后，历史期望运行的服务仍先是 Unknown。身份核对成功后只能作为外部服务复用；没有旧进程句柄的情况下不得恢复停止权。核对失败保留 Unknown 和原因，不自动重启、不按端口杀进程。

Unknown 的「检查」不能仅调用当前 inspect 并声称已完成恢复；开发时需抽出可复用的 reconcile/身份核对方法，或明确使用现有 Unknown ensure 分支，且保证核对失败不启动新实例。

服务事件建议写入日志根目录的独立 `service-events.jsonl`，包括没有执行 ID 的外部服务事件；包含 schema_version 和序号。事件日志必须有大小上限/轮转（建议 5 MiB × 2），失败通过诊断暴露，不能无限增长或刷聊天。它是诊断历史，不是通过重放事件恢复运行状态的 event-sourcing 系统。

登记继续遵循环境变量不持久化的现有约定。恢复后重启需要的环境由启动适配层重新提供；缺失时明确报配置错误，不能为了恢复方便把敏感环境值写进文件。

## 6. TUI 结果展示

- 服务操作完成只更新面板和状态栏，例如「qwen 已就绪」「preview 健康检查失败」。
- 原始 JSON 放诊断详情，不作为多段「系统」消息追加到聊天区。
- Agent 主动调用工具时仍返回结构化结果到模型上下文，不能因为 UI 去重而丢掉工具响应。
- UI 事件去重使用事件序号/操作 ID，而不是文本相同判断；重复健康失败保留计数与最近时间。
- 外部服务掉线、启动失败、停止未确认需要可见状态和原因，不只存在日志文件中。

## 7. 开发拆分与验收

建议按以下顺序交付，每一步都能独立测试：

1. 增加说明更新入口、持久化和提示词；补足普通受管服务无需身份 JSON 的启动方式。所有进程仍经 ProcessManager，不凭 Agent 文字认领未知进程。
2. 实现独立服务页和统一动作入口。复用现有 process_control/manager，展示自由文本和运行事实，支持预设及已登记项目服务。
3. 补齐必要并发约束和分页输出。测试并发启动、启动中停止、检查中 forget、旧探测晚到、说明更新与状态刷新交错、持久化错误及旧格式恢复。持续健康调度和独立服务事件文件是增强建议，不阻塞说明面板首版。
4. 做终端交互验收：宽屏与窄屏、中文长路径、无鼠标、Choice 卡片待答、空列表、长错误、外部服务无日志，以及列表变化后操作目标不漂移。

测试使用临时目录和本机伪 HTTP 服务，不要求本机安装模型。必要真实 smoke：Laya/Qwen 就绪检查、启动失败可见、停止后不自动复活；缺少模型时注明未验证，不能用模拟测试冒充实际可用。

验收重点：

- 用户不经过模型回复就能查看和管理服务，慢启动不冻结 TUI。
- 不重复启动同一服务，不停止外部服务，不用旧 PID 恢复控制权。
- 自定义服务重新启动使用原配置，不落到「预设仅支持 laya/qwen」错误。
- 服务面板、Agent 工具和进程页对同一服务的事实一致。
- Agent 可通过一段自由文本填写和更新服务情况，重启后仍能读到，不必提交用途、可访问、身份验证等固定字段。
- 更新说明不启停服务、不改变归属、不造成配置冲突；并发运行状态刷新不丢失最新说明。
- 普通受管开发服务器无需实现身份 JSON 才能登记；仅进程存活不能显示为健康协议已验证。
- 不再把周期性服务 JSON 反复塞进聊天。
- 新逻辑有对应回归测试，TUI/核心/进程相关测试与严格 Clippy 通过；最终构建可启动二进制。
