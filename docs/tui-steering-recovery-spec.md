# 运行中补充、执行恢复与方案审阅

这三个机制各自维护状态，共用已有对话记录和 artifact 目录。Lens、World 关系和新的用户级 session 管理不在本轮范围内。

## 运行中补充

聊天页输入文本后按 Enter：空闲时开始任务，执行时加入当前任务的有界补充队列。选择卡片等待回答时，输入仍优先作为卡片的自定义答案。斜杠命令继续由 TUI 本地处理。

- 补充先获得接收 ID，进入模型历史后才产生消费回执；队列满时保留输入草稿。
- 等待模型时可取消旧请求并携补充重新请求，未完成的流式回答不会提交到历史。
- 工具执行期间不因补充而取消正在执行的工具。收到结果后保留结果，跳过同批尚未开始的旧调用，给它们配对明确的未执行结果，再重新规划。
- 任务结束与补充到达同时发生时，成功任务会继续处理队列余项。失败或取消后不自动重新执行，余项保留到用户输入“继续”或 `/retry`。

队列、消费回执和历史快照放在 core 的 `SteeringInbox`；执行边界由 `AgentLoop` 维护。TUI 只负责接收、展示和持久化，不在界面层模拟工具执行顺序。

## 失败与恢复

超时、错误和取消不再把整轮历史退回起点。完整助手消息、已返回工具结果和用户补充都保留。没有返回结果的调用会补充协议配对，明确标记结果未知；这不是执行失败的证据，也不是重放授权。

`/retry` 将已保留证据交给 Agent，要求先检查结果未知的外部操作。它不是自动重试整批命令，也不承诺外部系统的 exactly-once。

每个既有 artifact 目录新增 `turn-checkpoint.json`：

- `messages`：最近提交的完整消息。
- `pending`：已接受但尚未进入历史的补充。
- `interrupted`：任务是否尚未正常完成。

core 在消息提交边界更新带 generation 的原子快照，TUI tick 只在变化时写入；文件采用临时文件、同步及 rename 替换，读取上限为 16 MiB。正常完成、失败和退出都会保存，既有 `/load` 与 `--resume` 同时恢复这些记录。恢复不会自行启动命令。

限制：进程被强制杀死或机器掉电时，最后一次 TUI 落盘之后的变化可能丢失。这里只保证已保存记录的恢复和协议完整性，不是每次外部副作用之前强制落盘的事务日志。部分流式回答不作为已确认结果恢复。

## 方案审阅

- `/plan 任务要求`：请 Agent 调查并通过 `update_spec` 发布完整方案，进入审阅页。
- `/plan`：仍查看普通任务步骤与进度。
- `F9` 或 `/spec`：打开方案页。
- `/spec 文件路径`：载入本地 Markdown 到审阅文档；不会直接改写源文件。
- `↑↓`：选择段落；`PgUp/PgDn`：滚动；`c`：写评论；`Enter`：提交评论；`Esc`：退出评论或回聊天。
- `a`：确认屏幕中的确切文档版本，并把确认交给 Agent 继续实施。

`SpecBroker` 是当前文档身份、revision 和确认状态的权威来源。`update_spec` 更新要求 `id` 与 `expected_revision`；更新会撤销上一版本确认。评论包含原版本、稳定段落 ID 及原文快照，旧段落即使被改写也仍可追溯。编辑评论期间文档更新时，提交会被拒绝并保留草稿，避免把旧评论悄悄挂到新段落。

TUI 在 `specs/` 下保存文档、评论及回复，使用存储 generation 防止旧快照覆盖。评论先保存，再作为用户输入或运行中补充交给 Agent；Agent 的最终回复显示在聊天，并记录在这批评论中。方案工具不阻塞等待人类确认。

审阅是模型指令与版本化交互流程，不是系统权限沙箱。没有全局禁用 Bash 或额外收紧普通任务权限；确认某方案也不授权无关任务。

## 验证重点

脚本 Provider 测试运行中补充、旧批次跳过、错误与取消后的工具结果保留；TUI 集成测试队列尾部竞争、失败后待处理项、恢复和 Spec 评论/确认链路；窄终端渲染测试验证导航及文档布局。真实模型是否充分遵循审阅要求，仍需日常交互验证。
