# Monad Agent 分层调度与上下文交接设计

> 状态：讨论草案，尚未实现；2026-10-05。
> 本轮只整理设计与验证路线，不修改运行时代码。
> 计算只是实验载体，目标适用于采购、库存、报销、查询等 monad。

## 1. 要解决的问题

monad 数量增长后，不能把所有 monad 说明、方法定义和历史对话放进每一次模型请求。系统应当按当前任务逐步发现能力，构造局部上下文，在局部任务完成后把结果交回原任务。

我们希望用户能实际观察到：

1. 主循环只看到 monad 入口的简短目录，不必看到全部方法。
2. 进入某项 monad 后，monad Agent 得到明确的任务交接包。
3. monad Agent 按需发现方法，只加载当前需要的方法定义。
4. 方法执行完成后，局部结果回填主任务中的对应位置。
5. 没有依赖且允许同时执行的任务可以并发；异步结果可以唤醒等待中的主任务。
6. 每次请求的上下文、工具集合及其变化可以检查，而不是只观察最终答案。

这不是要求每个工具都有一个 Agent。需要选择方法、补充信息或多步编排的 monad 才需要局部 Agent 循环；确定性的函数仍直接执行。

## 2. 项目现状与设计边界

当前实现依据：

- [agent_loop.rs](../crates/smallhead-core/src/agent_loop.rs)：每轮从 `state.messages` 转换全部可见消息，把 `self.tools` 的全部定义提交给 provider；工具通过循环逐个等待。
- [tool.rs](../crates/smallhead-core/src/tool.rs)：`calculate` 解析简单表达式，返回具体算子和参数提示；下一轮由模型调用算子。
- [demo.rs](../crates/smallhead-core/examples/demo.rs)：提示词同时介绍计算入口及具体算子。
- [v0.4-design.md](./v0.4-design.md)：大消息压缩列为后续工作。

因此当前 demo 证明的是“入口提示 → 方法调用”的基本流程，没有证明按需发现、隔离上下文、独立 monad 循环或并发回填。

已有 [Agent Loop 规格](../specs/02-agent-loop.md) 的外层 follow-up 与内层工具循环，处理的是对话生命周期。本设计的“主循环／monad 循环”是任务职责的分层，不能直接把原来的两层 while 当作已经完成本设计。

本草案不依赖 LanceDB 或向量检索。第一版使用静态 monad 注册表、内存任务状态和事件记录即可验证。

## 3. 模块与职责

| 模块 | 输入 | 职责与输出 |
|---|---|---|
| 主 Agent 循环 | 用户请求、主任务状态、monad 结果 | 分解任务、选择 monad、声明依赖、合并结果、回复用户 |
| monad 目录 | 查询或 monad 标识 | 返回 monad 名称、适用场景、简短描述和入口契约 |
| 上下文组装器 | 当前任务、相关事实、预算、阶段 | 生成当前请求的消息和可见工具集合，并记录组装依据 |
| 任务调度器 | 任务图、运行限制、完成事件 | 排队、派发、等待、取消、唤醒父任务 |
| monad Agent 循环 | 交接包、monad 说明 | 发现方法、选择方法、请求补充信息、局部多步执行 |
| 方法注册表与执行器 | 方法标识、参数、执行上下文 | 校验输入、执行函数或外部调用、返回结构化结果 |
| 任务状态与事件存储 | 状态转换及执行事件 | 保存事实来源、结果关联和可重放记录 |
| 观察界面 | 请求快照及事件 | 展示任务树、当前阶段、工具可见性、等待原因和 token |

初期按上述职责组织接口，不必立即增加对应数量的 crate。

## 4. 三种上下文及“画布”模型

### 4.1 完整状态

保存用户原始要求、主任务图、全部 monad 任务状态、交接包、执行结果和历史记录。完整状态存在于运行时与持久化层，不等于每次都发送给模型。

### 4.2 主循环上下文

包含用户当前目标、必要约束、主任务进度、monad 目录摘要和已完成 monad 的结果摘要。monad 内部的每一步工具调用默认不回灌到主循环。

### 4.3 monad 循环上下文

包含当前 monad 目标、输入、相关原话或引用、约束、完成条件、monad 方法目录及局部执行记录。它不需要携带全部主对话，但也不能只剩方法名称而丢失单位、对象、范围等必要信息。

局部上下文通过选择相关信息构造，不要求先对整个主对话做一次全局摘要。信息不足时返回 `needs_context`，由父任务补充，不能自行补造事实。

### 4.4 请求画布的更新

把 `RequestFrame` 看作模型当前读取的画布：消息、可见工具、当前目标和预算共同组成它。组装器负责修改画布，调度器决定何时加入新结果。

运行时状态可以持续更新，但普通模型请求提交后，其输入是已经发送的快照。修改本地 `RequestFrame` 不会改变正在生成的请求。新加载的方法和异步结果先写入任务状态，在下一次模型调用前重新组装并提交；需要立即响应时，可以取消当前调用后发起新调用。不能把框架 middleware 更新状态理解为远端请求实时读取共享内存。

每次实际提交记录 `frame_revision`，关联 `request_id`、`task_id`、事实与工具集合的快照，便于事后重建模型当时所见。未发送的状态更新与已发送快照分别记录。

全局历史压缩是另一个独立问题；即便尚未实现全局 compaction，也可以先完成局部 monad 上下文隔离。

## 5. 发现、交接、执行与回填

### 5.1 发现

主 Agent 只获得 monad 入口的简短信息，例如“计算 monad：处理数值运算；提交表达式与所需约束”。monad 很多时，进一步通过目录查询缩小候选集合，避免连目录摘要也无限增长。

选择 monad 后，monad Agent 得到本 monad 的方法摘要；选定方法后才加载完整参数 schema。方法目录大时，同样允许查询，不强制一次注入整个 monad 的方法集合。

工具出现在文本里不等于已经可调用。运行时必须同时维护当前可见定义与实际执行许可，拒绝未在当前任务范围内开放的方法。

### 5.2 交接

交接包应明确“为哪个父任务完成什么”，不能仅仅传一段自由文本提示。

```json
{
  "task_id": "calc-1",
  "parent_task_id": "main-1",
  "business_id": "calculation",
  "objective": "计算一百加一百",
  "inputs": {"expression": "100+100"},
  "relevant_context": [],
  "constraints": [],
  "completion_criteria": "返回数值结果及原始表达式",
  "depends_on": [],
  "result_slot": "calculations.first",
  "budget": {"max_steps": 6, "timeout_ms": 30000}
}
```

字段是草案，不是已经存在的 API。实际 monad 的相关上下文可以包含单位、记录标识、时间范围、用户限制及来源引用；敏感数据不应因派发任务而默认复制全部历史。

### 5.3 执行

monad 循环反复执行“读取局部状态 → 选择下一步 → 方法执行 → 接收结果”，直到满足完成条件或进入等待、失败、取消状态。

第一版限制为主任务加一层 monad 任务，不开放无限递归委派。每个 monad 具有独立步数与时间预算，局部失败不能让整个会话直接崩溃。

### 5.4 回填

```json
{
  "task_id": "calc-1",
  "parent_task_id": "main-1",
  "result_slot": "calculations.first",
  "status": "completed",
  "output": {"expression": "100+100", "value": 200},
  "evidence_refs": ["execution-1"],
  "error": null
}
```

调度器按任务标识回填，不能依靠结果到达顺序。主 Agent 得到结果与必要证据摘要，再判断原始请求是否全部满足。

`task_id` 表示 monad 任务，`tool_call_id` 表示一次模型工具调用，`attempt_id` 表示一次执行尝试。三个概念分别保存，避免重试或多次方法调用覆盖结果关联。

## 6. 主循环与 monad 循环如何协作

概念流程：

```text
用户请求 → 主循环构造任务图 → 调度器派发就绪任务
                              ├→ monad A 循环 → 方法执行 → 结果 A
                              └→ monad B 循环 → 方法执行 → 结果 B
结果事件 → 调度器回填任务状态 → 唤醒主循环 → 继续任务或回复
```

主循环提出任务计划，调度器执行计划。模型负责判断 monad 语义上的独立性，程序负责执行并发数量限制、依赖条件、权限及已知资源冲突检查。

异步意味着主任务可以等待结果而不阻塞整个服务；并发意味着多个任务的执行时间有重叠。两个概念分别实现，先能可靠等待一个任务，再增加多个任务。

主任务等待期间仍可接收用户取消或修改。修改会增加 `task_revision`；旧版本结果保留记录，但不能直接当作新版任务的完成依据。

## 7. 并发与依赖规则

只有同时满足以下条件才派发：前置任务已满足、没有冲突资源、获得执行许可、预算和并发配额足够。

- 独立只读查询一般可并发，例如分别查询两个商品的库存。
- 后续需要前一步输出时必须等待，例如先查订单再用订单号办理 monad。
- 对同一资源进行修改时需要串行或明确的事务策略。
- 用户明确要求先后顺序时保留顺序，即使数学上没有数据依赖。
- 并发判断存在不确定性时先串行，并记录原因。

模型输出依赖与并发建议；运行时根据声明的资源和方法元数据做检查，不能只凭模型说“可以并发”就绕过执行约束。

第一版采用批次汇合：同一批次就绪任务全部进入终态后，主循环统一处理结果。之后再加入“某个结果到达就推进其后继”的增量调度。

批次中的一个任务失败，独立任务可以继续；依赖失败任务的后继标记为阻塞。最终回复可以呈现部分成功，但必须明确未完成部分。

## 8. 状态、失败与恢复

任务状态建议：`pending → ready → running → completed`，并支持 `waiting_context`、`waiting_children`、`failed`、`cancelled`、`blocked`。

| 情况 | 处理 |
|---|---|
| 输入缺少 monad 事实 | 进入 `waiting_context`，返回缺少字段与原因 |
| 方法参数不合法 | 返回结构化校验错误，允许 monad 循环在预算内修正 |
| 暂时性网络失败 | 按方法策略有限重试，并记录 attempt |
| 超时 | 记录超时并取消本地等待；有副作用的方法还需核对实际执行状态 |
| 重复结果事件 | 按任务、版本与执行尝试去重，不重复回填 |
| 主任务取消 | 向子任务传播取消；已完成的外部写入不能假装撤销 |
| 迟到结果 | 保留审计记录，不覆盖已取消或更新版本的任务 |
| 写操作结果不确定 | 先查询执行状态，避免盲目重试造成重复写入 |

第一版可以只实现进程内状态；恢复阶段必须持久化交接包、结果、任务版本和必要事件。重启后不能把所有 `running` 任务直接重新执行，尤其是有外部副作用的任务。

## 9. 流式工具参数问题作为独立前置项

用户提供的日志包含 `{`、`"a":` 等不能单独解析的 JSON 片段。当前 AgentLoop 会尝试逐条解析 delta，而代码注释约定 provider 提交累计完整参数，说明事件契约需要先统一。

验证时区分原始传输片段与交给执行器的完整参数。以多个工具交错返回、参数分片和流中断为测试输入；完整参数校验通过前禁止执行。不要通过调整 monad 路由提示词掩盖事件层问题。

此项只作为设计前置检查，本轮不修改解析代码。

## 10. 可观察性：让分层实际可见

每个请求或画布版本记录：

- `request_id`、`frame_revision`、`task_id`、`parent_task_id` 和阶段。
- 发送的消息来源、可见 monad／工具名称、估算 token 和 provider 实际 usage。
- 选择哪些事实、略去哪些历史的摘要及其依据。
- 派发、开始、结束、等待、取消和结果回填事件。
- 上下文不足、超预算、重试与阻塞的原因。

默认日志输出摘要，完整请求快照在本地调试模式按需开启。展示层优先提供任务树和每一步请求详情，不要求先开发复杂 UI。

验收时必须能回答：“这个 monad Agent 为什么知道这两个参数？它看到哪些方法？它为什么没有并发？这个结果回填到哪里？”

## 11. 分阶段工作与验收

| 阶段 | 工作范围 | 可评审交付与验收 |
|---|---|---|
| P0 协议基线 | 明确流式参数事件契约，记录当前请求内容 | 分片与多工具输入不串数据，不执行未完成参数；保存现状轨迹 |
| P1 单 monad 交接 | monad 目录、任务交接包、局部循环、结果回填 | 主请求没有全部方法定义；monad 请求没有无关主对话；结果关联准确 |
| P2 多任务顺序 | 任务图、依赖、主任务等待、失败状态 | “先 A 后 B”严格有序；B 可以引用 A 的输出；失败不伪装成功 |
| P3 受控并发 | 并发上限、资源检查、批次汇合、去重 | 独立任务执行重叠；乱序返回仍正确回填；冲突任务串行 |
| P4 上下文规模 | 方法按需发现、预算、信息补充、画布追踪 | 大量无关 monad 与历史不全部进入局部请求；关键信息不遗漏 |
| P5 长任务可靠性 | 超时、取消、恢复、增量唤醒 | 重启与迟到结果不造成重复副作用或旧结果覆盖 |

每阶段先用可控的模拟 provider 检验调度与数据关联，再用真实模型验证方法选择与交接信息是否充分。模拟测试证明状态机行为，不能代替真实模型的选择能力测试。

## 12. 第一组实验

1. **基线案例**：“一百加一百，然后再算一百乘以一百”。建立两个任务，保留先后关系，分别回填 200 与 10000，最后统一回复。
2. **允许并发**：“分别计算这两项，没有先后要求”。相同输入，观察调度是否可以并发，而非只看最终答案相同。
3. **数据依赖**：“先算一百加一百，再把结果乘以一百”。后一个任务依赖前一个输出，最终为 20000。
4. **长历史**：加入大量无关对话，确认局部 monad 仍只有必要输入与方法定义。
5. **monad 约束**：计算报价时加入币种、税率、舍入规则，确认交接没有只保留数值而丢失约束。
6. **非计算 monad**：库存查询与采购草稿，验证抽象没有依赖表达式解析器；第一版只用模拟数据和可逆操作。
7. **异常交接**：缺参数、错误方法、失败、重复结果、乱序返回、取消与超时。

每次记录正确率、主／子请求 token、工具定义数量、模型调用次数、执行耗时及重试次数。分层可能增加模型调用次数，因此不预设总费用或延迟一定降低；通过同输入对照现有全量上下文流程评估。

## 13. 本轮待评审的决定

建议先接受：主任务加一层 monad 循环；显式交接包与结构化结果；静态目录起步；先串行再受控并发；第一版批次汇合；每次上下文变化可追踪。

后续重点讨论：

- monad 入口如何描述，才能让模型可靠选择而不膨胀主上下文？
- 哪些 monad 确实需要 Agent 循环，哪些直接调用方法即可？
- 主任务传递相关上下文的最低要求是什么，信息不足怎样补充？
- monad 方法如何声明资源冲突、副作用、重试与幂等性？
- 是否需要每个结果立即唤醒主循环，还是阶段性汇合已足够？
- 怎样给不同 monad 分配上下文、步数与时间预算？

文档评审后再选择 P0/P1 的实现范围；本草案不意味着上述功能已经开发完成。
