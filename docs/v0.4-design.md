## v0.4 一、Permission 系统设计

### 1.1 设计目标(为什么要做)

- **当前空白**:`agent_loop.rs::run_one_turn` 拿到 tool_call 就直接 `ToolKind::execute`,没有任何拦截层。
- **真正风险**:Bash 工具一旦加进来(中期),就具有「删光 `~` 树」的潜在能力——必须有用户授权机制。
- **可观测性**:要 audit 谁(哪条 tool_call)在什么时候改了哪个文件,以便 panic recovery 时回滚。

### 1.2 big-head 是怎么做的(借鉴)

`big-head/crates/big-head-loop/src/tools/policy.rs:7-206`:

```rust
pub(super) fn pipeline_policy_violation(&self, call: &ToolCall) -> Option<String> {
    // ... 9 个独立的 policy 检查:
    // 1. writes_receipt           — 拒绝写 ToolExecution / UserQuestion
    // 2. writes_activity          — 拒绝写 ActivityRun
    // 3. writes_a2a_origin        — 拒绝写 A2aOrigin
    // 4. system_id_collides       — define_tool 不能撞 runtime tool 名
    // 5. writes_dream             — 拒绝写 DreamExperiment
    // 6. writes_interpretation    — 拒绝写 interpretation 元数据
    // 7. allowed_tools            — 工具白名单
    // 8. mutates_tick_action      — TickAction 必须用专用 API
    // 9. writes_reserved          — 拒绝写运行时保留 component
}
```

**借鉴要点**:政策函数返回 `Option<String>`(None = 放行,Some = 拒绝 + 解释)。
这是典型的「规则 → 决策」模式,**可移植到 smallhead**(只是规则内容不同)。

### 1.3 smallhead 的 policy 设计(三档)

| 档位 | 触发场景 | 行为 |
|---|---|---|
| **YOLO** (默认开发) | 内部脚本、CI | 全部放行,只 audit |
| **Safe** (TUI 交互默认) | 用户在前 | 写操作 + 路径外读 → 弹出 y/n 确认 |
| **Sandbox** (生产/agent-to-agent) | pipeline / 自动化 | 严格 allowlist + 路径 jail |

API 设计(草案):

```rust
pub enum PolicyDecision {
    Allow,
    Deny { reason: String },
    Ask { question: String, wait: WaitKind },
}

pub trait Policy: Send + Sync {
    fn decide(&self, ctx: &PolicyContext, call: &ToolCall) -> PolicyDecision;
}

/// 默认实现:链式 fallback,YOLO + Safe 合并实现
pub struct DefaultPolicy {
    yolo: YoloPolicy,        // 全部 Allow + 写 audit log
    safe: SafePolicy,        // 写操作 Ask
    sandbox: SandboxPolicy,  // 路径 + 工具白名单
}
```

### 1.4 配置持久化

- 路径:`~/.smallhead/policy.json`(首次启动根据 CLI flag `--policy-mode` 写默认)
- 字段:`{mode, allowed_paths: Vec<String>, denied_tools: Vec<String>, custom_rules: Vec<Rule>}`
- Audit log:`~/.smallhead/audit/YYYY-MM-DD.jsonl`(append-only,每天一个文件)

### 1.5 接入点

`agent_loop.rs::run_one_turn` 内 while 循环,在 `tool_kind.execute(...)` 之前插入:

```rust
match self.policy.decide(&ctx, &tool_call) {
    PolicyDecision::Allow => { /* 继续执行 */ }
    PolicyDecision::Deny { reason } => {
        // 推 ToolResult { is_error: true, content: "denied: ..." } 直接跳到下一轮
        state.messages.push(ToolResult::denied(&tool_call.id, &reason));
        continue;
    }
    PolicyDecision::Ask { question, wait } => {
        match wait.blocking_ask(&question).await {
            AskResponse::Yes => { /* 继续 */ }
            AskResponse::No => { state.messages.push(ToolResult::denied(...)); continue; }
        }
    }
}
```

**关键**:`Deny` 不应该让 Loop 崩——只是把「拒绝」作为 ToolResult 喂回 LLM,LLM 看完自己调整行为(这是 Anthropic / OpenAI 的标准 pattern)。

## v0.4 二、Session 持久化设计

### 2.1 设计目标

- **崩溃恢复**:进程崩了 / Ctrl+C 退出 / 网络断 → 重启能 resume 接着干
- **历史查询**:可以看「昨天这个 session 我让它做了什么」
- **checkpoint rollback**:用户可以「回滚到上一步」(commit 前)

### 2.2 big-head 是怎么做的(借鉴)

`big-head/crates/big-head-save/`(~1300 行,设计文档级代码):

- `journal.rs`(333 行)— append-only journal,记录每一次 world mutation
- `snapshot.rs`(289 行)— 定期 full snapshot,反序列化整个 World
- `persistence.rs`(680 行)— `checkpoint()` 写入 + `restore()` 恢复
- `reclamation.rs` — 回收旧 journal(防止无限增长)

**核心模式**:Journal(细粒度,append-only)+ Snapshot(粗粒度,full image)。

### 2.3 smallhead 的持久化设计(简化版)

smallhead 的 state 比 big-head 简单很多——只有一个 `Vec<AgentMessage>`(已经在 `state.messages`)。
**MVP 不需要 journal**,直接单文件 snapshot 就够:

```rust
// 文件:~/.smallhead/sessions/{session_id}.json
{
    "id": "uuid-v7",
    "created_at": 1730000000000,
    "updated_at": 1730000005000,
    "system_prompt": "...",
    "messages": [AgentMessage, ...],  // 全部消息
    "summary": "user did X, then Y, got Z"  // LLM-generated 摘要(可选)
}
```

SQLite 适合「需要查询历史 session」的版本,MVP 用单文件 JSON + index 文件:

```
~/.smallhead/
├── policy.json                 # v0.4a
├── audit/2026-10-04.jsonl      # v0.4a append-only
└── sessions/
    ├── index.json              # session_id → metadata 列表
    ├── 0192f7a8-...json        # 完整消息
    └── 0192f8b3-...json
```

### 2.4 三个核心 trait

```rust
pub trait SessionStore: Send + Sync {
    async fn save(&self, session: &Session) -> Result<(), SaveError>;
    async fn load(&self, id: &SessionId) -> Result<Session, SaveError>;
    async fn list(&self) -> Result<Vec<SessionMeta>, SaveError>;
}

pub struct Session {
    pub id: SessionId,
    pub created_at: i64,
    pub updated_at: i64,
    pub system_prompt: String,
    pub messages: Vec<AgentMessage>,  // 直接复用 core 的类型
}

pub struct SessionMeta {
    pub id: SessionId,
    pub created_at: i64,
    pub updated_at: i64,
    pub summary: Option<String>,
    pub message_count: usize,
}
```

### 2.5 resume 协议

TUI / CLI 增加:
- `--resume <session_id>` → 加载 messages 到 AgentLoop state,然后进入正常对话
- `--list-sessions` → 打印 index
- 每次 turn 结束后自动 save(不是 panic 才 save)
- `/save` 命令在 TUI 内部手动触发 save

### 2.6 大消息的压缩策略(后续)

当 messages 超过阈值(比如 100 条或 50k token),触发 `Compaction`:
- 让 LLM 生成摘要
- 把历史折叠成一段 summary(用 AgentMessage::Compaction 变体)
- 这一块 pi-muto 里有 `Compaction` variant,目前 `to_llm` 返回 None(不进 LLM)——需要先把它 enable

## v0.4 三、Panic Recovery(简化)

不重做:

- **进程级 panic**:`std::panic::set_hook` 把 panic info 写进 `~/.smallhead/audit/panic-{ts}.json`
- **tool execution 中断**(比如 ctrl-c 在 Bash 运行时):Tokio `CancellationToken` 已经在 ToolContext 里预留 `cancel_rx`,接上 `signal::ctrl_c()` 即可
- **Provider 流中断**:`MiniMaxProvider` 的 reqwest 加 `retry_with_backoff`(指数退避 3 次)

## v0.3 短期:Progress 通道(对比 + 代码骨架)

> 用户原话:「短期(1-2 commit):流式 token 显示(需要先在 AgentLoop 加 progress 通道)」

### 数据流

```
AgentLoop::run_one_turn (内部)
    │
    ├── ProviderEvent::ContentBlockDelta { text }   ──┐
    │                                                 │
    ├── tool_call 触发                                  ├── 推送到 mpsc::Sender<TurnEvent>
    │   ├── start                                      │
    │   ├── end                                        │
    │   └── result                                     │
    │                                                 │
    └── (turn 结束) ───────────────────────────────────┘
                                                          ↓
                                            TUI 订阅,实时渲染
```

### API 草案

```rust
// 现在的:
pub async fn run_one_turn(&mut self, user_msg: AgentMessage) -> Result<LoopSummary, ...>;

// 新增:
pub fn progress_tx(&self) -> mpsc::Sender<TurnEvent>;
pub async fn run_one_turn_with_progress(
    &mut self,
    user_msg: AgentMessage,
    tx: mpsc::Sender<TurnEvent>,
) -> Result<LoopSummary, ...>;

pub enum TurnEvent {
    TextDelta(String),       // 助手的字符
    ToolCallStart { id, input },   // LLM 决定调工具
    ToolCallEnd { id, result },    // 工具执行完毕
    TurnEnd { summary },          // 一轮结束
}
```

实现代价:`MiniMaxProvider::stream` 已经返回 `Stream<Item = Result<ProviderEvent>>`,
我们 clone 出一个 channel,在 `collect_assistant_stream` 内部加 `tx.send(...)` 就够了。

## v0.3 中期:Bash/Read/Edit/Write 复刻度

> 用户原话:「Bash/Read/Edit/Write 在 bighead 和 codex 这些都有范例,我们看看复刻出来的程度是怎么样」

| 工具 | codex 怎么做 | big-head 怎么做 | smallhead MVP(草案) | 复刻度 |
|---|---|---|---|---|
| **Bash** | `SandboxedCommand` + timeout + 输出 truncate | `execute_cli`(白名单 cmd) | `Command::new(...).timeout(30s).output()`,路径 jail cwd | 70%(无 sandbox) |
| **Read** | offset/limit + expected_sha256 paging | 同 big-head read.rs 设计 | `fs::read_to_string` + 分页(直接抄 codex paging 协议) | 90% |
| **Edit** | search_text + replace,失败时报「expected N matches」 | 无(只有 ECS update) | `read → str::replace → atomic_write`,失败给「0 matches」/「multiple matches」错误 | 75% |
| **Write** | atomic rename + backup | 无 | `fs::write` + 备份原文件到 `.bak` | 85% |

**共通前置**:所有 4 个工具的 input schema 必须带 `path` 字段,且 Policy 层必须先做「path 在 allowed_paths 白名单内」的检查——这就是为什么 Bash/Read/Edit/Write **必须** 跟 permission 系统一起做。

## 推荐执行顺序

1. **v0.3 短期(progress 通道)** — 解锁 TUI 流式显示,体验提升最明显
2. **v0.3 中期(Bash/Read/Edit/Write)** — 但只做工具本身,**不接 policy**(先用 YOLO 模式裸跑)
3. **v0.4a(policy)** — 工具到位后,policy 才有意义
4. **v0.4b(session 持久化)** — 跟 policy 并行,但可独立 demo
5. **v0.4c(panic recovery)** — 兜底,最后做

> 备选:把 4 + 5 提前——「有持久化但没 policy」不算真交付,但「有 policy 但没持久化」反而能用(每次崩就丢数据)。
