# Lens 插件运行机制草案

2026-10-19，整体机制讨论稿。已落地可组合 loop 策略、JS worker、按回合隔离和 TUI load/reload/unload，实际 API 见 [smallhead-lens](../crates/smallhead-lens/README.md)。以下完整插件生命周期、工具注册、界面贡献等仍为后续建议，不能视作全部实现。

策略接口的进一步抽象、组合规则和论文/工程参考见 [可组合 Loop 策略：抽象与参考](lens-loop-policy-abstraction-and-references.md)。

## 定位

Lens 是 Smallhead 的通用扩展包。Learning Agent 是第一个完整应用，不把学习工具硬编码进 TUI。未来项目研究、资料管理、业务系统都可用同一机制开发、安装、加载、停用和卸载。

定位修正：Lens 不仅注册业务工具，还可以用代码改变 agent loop 的策略和环节，包括 system 构造、每次模型请求的上下文与工具视野、工具调用处理、后续验证、继续或结束。JS 是这种运行策略的实现语言之一，不限定为资料库适配代码。

对外继续用 Lens 这个名称。内部可区分 LensPackage（定义和代码）、LensInstance（配置与运行资源），不再引入一套平行的插件产品概念。Monad 仍表示实际执行工作的 agent。

“万物插件”表示业务和可替换能力通过统一扩展接口接入，不要求把取消、消息协议完整性、资源归属、预算等基础保证也交给插件自行实现。Smallhead 保留小型运行内核和宿主界面。

## 核心：Lens 可以编写运行策略

基础循环仍是模型推理、行动、观察、再推理。Lens 能改变每一步如何准备、行动如何提供给模型、结果如何组织，以及什么情况下继续、转交、等待或完成。它不必每次添加一个固定 Planner → Teacher 流程，也不需要复制整份 Rust loop。

应分清两种控制：system、工具描述与上下文影响模型如何理解和选择；代码负责真正的分支、调用规则、验证与状态转移。只改一句 system 不能保证某一步必定执行，只靠代码读取文本也不能证明模型理解正确。

建议提供以下策略边界，名称为示意，尚不是现有 API：

| 边界 | Lens 可以改变什么 |
| --- | --- |
| prepare_turn | 构造领域 system、初始上下文、可用能力与本轮策略状态 |
| before_model | 按当前证据和环节调整 system、上下文投影、工具描述、可见工具与允许的模型参数 |
| after_model | 根据响应和当前状态选择继续流程；区分候选回答、工具请求与后续检查 |
| before_tool | 校验或规范化参数、解析模型可见的工具别名、选择已注册的执行适配，或明确拒绝本次调用 |
| after_tool | 保留真实结果并组织给模型看的观察，更新策略状态，决定下一次需要补什么 |
| before_finish | 允许完成，或提出有依据的继续请求、委派、等待用户输入；受原有预算和取消约束 |

工具的名称、说明和 schema 也是 Lens 的表达方式。例如同一检索后端可以对模型提供“找教材中解释某个概念的段落”或“核验项目实现”两种不同语义入口。模型看到的 schema 必须与对应适配一致，不能描述一种能力却静默执行另一种副作用。

策略可以具有跨模型波次的本轮状态，不是一次性启动配置。Lens 代码版本在本轮固定，状态和下一次请求可以随工具观察、用户补充和子 Monad 报告而变化。

### 学习场景的实际差异

用户要求“三本教材怎样解释同一个概念”时，Lens 可以：

1. 根据任务构造强调原文对照的 system，并让检索、原文读取、引文核对工具具有清楚的适用说明。
2. 根据已取得的材料调整下一次请求的上下文，避免把多份全文反复塞进去；必要时使用已有 Monad 调度研究任务。
3. 若模型准备结束，但明确要求的资料核对还未完成，选择继续并提示缺少什么；来源不可得时允许如实说明缺口，不无限重试。
4. 用户只问一句简单追问时，直接沿用默认循环，不强制走研究、解释、练习全套阶段。

示意策略：

```js
// 伪代码：不是当前可调用的 SDK。
export function beforeFinish({ state, candidate }) {
  if (state.needsSourceCheck && state.sourceCheck === 'pending') {
    return {
      type: 'continue',
      guidance: '先核对所引用的原文；无法取得时说明缺口。',
    };
  }
  return { type: 'finish', candidate };
}
```

needsSourceCheck 来自显式任务要求或已记录的策略决策，sourceCheck 依据实际执行回执更新，不能由模型一句“已验证”直接置为成功。这里检查流程证据，不保证引用在语义上支持整个结论。

### 与 Rust 执行底座配合

当前 `AgentLoop::run_turn_inner` 保留请求执行、响应提交、工具执行与收尾机制，在 prepare_model、before_tool、after_tool、before_finish 四个真实边界开放 `LoopPolicy`/`PolicyStack`。未加载 Lens 时沿用默认决定；上表其余扩展面尚未落地。

JS 可以通过有类型的指令请求下一步模型调用、宿主工具执行、委派、等待或完成；由 Rust 统一执行和记录效果。这样它能编写不同流程，仍复用 Provider、工具结果配对、历史压缩、steering、预算和资源清理。插件不需要自行接管模型连接或重做协议。

特别需要改变“无 tool call 就直接结束”的固定决策点，让默认策略保持现状，而 Lens 策略能返回继续或等待。插件错误须明确归因，不能静默撤掉领域策略后声称按原要求完成。继续请求仍受预算限制，不自动重放已执行的副作用。

工具结果的原始回执与模型可见观察分别保留；改写观察不能伪造执行成功、篡改原始结果或抹去调用身份。流式文本也应区分正在生成的候选与已通过收尾判定的最终回答，策略要求继续时不再把候选标成任务完成。

这些是可修改的 loop 行为，不是要求通过字符串替换动态修改 Rust 源码。具体运行策略模块、worker 协议和 SDK 应作为同一项开发。

## 参考与实际差异

本地 `plugins/dsh-smallhead` 已展示 DSH 的这些模式：

- `inject` 声明所依赖的宿主服务。
- `apply(ctx, config)` 注册工具、HTTP 路由等能力。
- `ctx.effect` 管理注册返回的释放函数。
- 包中 host/client 两个入口各自注册后端能力和界面 slot。

这些观察来自本地实际插件及其 README，不是对最新 DSH 全部实现的审计。可以借鉴依赖、注册、作用域和释放的结构；Smallhead 的 TUI、Rust 所有权及进程管理需要自己的实现。

## 一个 Lens 可以贡献什么

| 扩展面 | 例子 | 宿主职责 |
| --- | --- | --- |
| 运行策略 | 每次请求的 system、工具视野、环节分支、继续与完成规则 | 执行有类型的下一步指令，保持协议与取消有效 |
| 工具 | 检索教材、核对引文、更新学习位置 | 工具协议、命名冲突、调用与结果关联 |
| 上下文 | 选当前章节、相关困难、领域约束与教学策略 | 注入位置、预算、来源与冲突报告 |
| Monad 角色 | 教材研究、练习审阅 | 统一 AgentLoop、独立身份、工具集合与协作 |
| 界面 | 课程目录、原文引用、资料列表 | 渲染、焦点、滚动、输入路由 |
| 命令与动作 | 导入资料、切换课程 | 命令发现、执行回执、取消 |
| 数据适配 | SQLite 课程库、本地索引 | 实例配置、迁移入口、数据归属说明 |
| 服务需求 | 索引服务、脚本 worker、MCP server | 复用现有管理器，区分本实例资源与外部服务 |
| 生命周期事件 | 实例加载、停用、回合结束记录证据 | 事件身份、顺序、超时、错误及释放 |

不是每个 Lens 都要提供这些能力。纯 Markdown Lens 可以只提供策略和上下文配置。带代码的 Lens 使用同一包管理与生命周期，不另开“学习模式”的专用加载器。

## 三种代码形态与统一宿主接口

建议先固定宿主契约，再确定全部执行后端：

1. 声明式 Lens：配置、策略、上下文选择、对已有能力的引用，无代码 worker。
2. 脚本 Lens：倾向先支持进程外 JS worker，便于像 DSH 一样直接开发与修改；既可注册工具，也可实现逐波次运行策略，通过带版本的消息协议返回下一步决策和受支持的效果请求。
3. Rust 内置扩展：以编译期 factory 接入相同注册表，用于现有高性能或已有 Rust 领域实现；不把 Rust 动态库 ABI 作为首版外部插件接口。

JS worker 进程是生命周期与故障处理边界，不自动构成文件系统或网络沙箱。是否限制其访问范围必须由实际运行环境实现，不能仅凭 manifest 宣称隔离。

MCP 继续承担外部工具协议。它可以被 Lens 引用和复用，但单独一个 MCP 连接不能表达逐步运行策略、教学策略、上下文准备、TUI slot、Lens 版本及实例配置。不把所有扩展都硬塞成 MCP tool，也不另造一套 MCP 替代协议。

## 包与依赖

```text
learning/
  lens.toml       包标识、版本、宿主 API 版本、入口、依赖、能力声明
  instructions.md 教学策略
  loop.mjs        可选运行策略、环节状态与决策
  host/           可选脚本代码或已有能力的绑定
  views/          可选声明式视图
  examples/       可重放场景与预期
```

这里是建议目录，不是已支持的格式。数据目录、用户身份、凭据、数据库路径属于本机实例配置，不进入可交换的包正文。安装包和插件产生的用户数据分开保存。

依赖区分“需要某个宿主 API”“需要另一个 Lens 的能力”“需要一个外部服务”。加载前检查版本和循环依赖，缺少依赖时显示原因。依赖停用时不能假装下游仍正常工作；资源释放按依赖关系处理。

每项注册绑定包 id、实例 id 和运行代次，避免旧 worker 的延迟响应落到新实例。工具默认使用命名空间，用户看到的 label 与模型可见 schema 由宿主一致维护。

## 注册和资源释放

借鉴 DSH 的 context/effect：宿主发给 Lens 的 context 提供受支持的注册 API；每次注册都返回 handle，由该实例的资源集合持有。

实例可以登记工具、视图、上下文提供器、订阅、后台任务和自己创建的资源。卸载不是只从菜单删掉名字；必须释放登记的能力、结束自有任务、关闭自有 worker，并报告清理结果。

宿主不能靠插件自觉清理来维持基本边界。Rust 侧以实例 Scope 持有资源和 CancellationToken，提供显式异步 shutdown；Drop 只作兜底。进程外 worker 崩溃时宿主仍能撤销其注册并结束待处理调用。

借用、共享和本实例独占的服务分别处理：释放一个 Lens 不应关闭其他 Lens 仍在使用的共享服务，也不能终止外部用户自己启动的服务。服务进程沿用现有 ServiceManager 或 MCP manager，不给 Lens 再造第三套管理器。

## 加载、启用、停用与卸载

| 动作 | 语义 |
| --- | --- |
| 安装 | 包在本地可用，尚未启动其代码 |
| 加载与启用 | 校验依赖和配置，激活实例，成功后发布注册能力；失败撤销已登记资源 |
| 停用 | 停止接收新的使用请求，排空或取消自有工作，释放运行资源，保留包与用户数据 |
| 卸载 | 完成停用后移除包；删除课程、记忆等数据必须是独立动作 |
| 更新 | 准备并校验新版本，再切换后续使用；保留可回退的旧版本记录 |

清理失败必须展示 Failed/Unknown 及原因，不能仅因为超时就声称已完全卸载。

回合开始取得不可变 Lens 配置和工具快照。现有回合持有旧实例的使用凭据，新回合使用新版本；旧实例停止新准入并等待已有使用结束，之后再释放。紧急停用需明确取消受影响工作并修复完整工具协议，不能让已发给模型的工具突然无结果消失。

“能够安装、启停、更新而不重启宿主”与“当前推理到一半随意换实现”是不同承诺。首版先实现前者和回合边界切换。

## Lens 的组合

统一包管理本身不等于实现 Lens 叠加。组合需要实际生成本轮的上下文与能力视野：

- 明确哪些 Lens 适用、采用哪个版本以及谁决定启用；不把所有已安装包都塞进每轮上下文。
- 上下文按来源合并和去重，保留引用及预算；互斥策略显式报告，不依赖偶然加载顺序。
- 能力按宿主允许的范围提供给主/子 Monad；包依赖不自动授予额外权限。
- 记录本轮组合和来源，以便解释“为什么用了这种教学方式”及复现失败。

代码策略也需要组合。请求准备可按显式顺序变换下一次请求，结果观察可以逐层处理；多个策略都要决定 continue/finish/delegate 时，需要宿主明确的控制权规则，不能让最后一个回调偶然覆盖前一个。首版建议一个主要流程控制策略，其他 Lens 在声明的边界包裹或增强它。组合顺序与决策记录到诊断中。

中间件可以让外层 Lens 基于内层策略结果再次决定，但进程外协议不能传递 Rust/JS 函数对象。SDK 的组合语法需要由宿主编排调用阶段及序列化回执实现；先定义该协议，不把多个互不相关的事件监听器误称为流程组合。

Learning Lens、当前教材范围、个人解释偏好可以组合。它们共享一次具体问题下的上下文选择，而不是各自重复完整教学循环。第一版不承诺通用组合代数或任意动态 DAG 调度。

## TUI 与 A2A

TUI 提供通用 Lens 管理页：安装版本、依赖、启用状态、配置、错误、贡献的工具/视图以及卸载动作。领域视图走统一 slot，第一版优先支持列表、Markdown、引用与表单；宿主统一处理键盘和滚动，不要求每个 Lens 接触 ratatui 内部结构。

A2A 是编写和交换 Lens 的入口之一，直接编辑本地文件、用户聊天要求修改和安装现成包同样支持。交换候选正文与版本，不交换个人学习数据库。外部 agent 提交具体差异后，宿主保存回执；有用户授权时采用对应版本，不能由对方自报用户身份来完成启用。

现有 A2A 与 TUI 需要共用宿主装配层，按各自能力范围取得可用工具和 Lens；不应保持各写一份 AgentLoop 工具清单。复用装配不代表两个入口拥有相同权限或直接共享可变 history。

## Rust 组织建议

在 core 中提取默认 loop 策略、阶段快照与有类型的下一步指令；执行底座统一处理模型、工具和协议。`smallhead-lens` 独立 crate 负责 manifest、registry、scope、实例生命周期、worker transport、脚本策略适配与版本快照。它依赖 core 公共接口，core 不反向依赖具体插件、JS 运行时或 Learning 业务。

另设宿主装配模块组合 AgentLoop、Lens registry、进程/MCP 管理器和输入来源；TUI/A2A 都通过它构造运行环境。TUI 只负责通用管理与呈现适配。

学习数据与确定性核对可继续留在 Learning Agent library 或 worker 内，不搬进 Smallhead core。已存在的 ExternalTool 是可复用的调用适配层，不是完整的插件生命周期实现。

## 推荐第一阶段

先做一条通用、能实测的纵向链路：加载本地 Lens → 代码构造 system 和工具视野 → 模型调用工具 → Lens 依据真实结果改变下一步 → 收尾判定 → 停用清理 → 更新并回退。首个验收必须证明相同执行底座因 Lens 策略而产生不同的实际流程，不能只验证多注册了一个工具。

用两个不同 Lens 验收接口：一个极小演示 Lens 验证默认透传、条件继续与装卸，一个 Learning Lens 验证动态 system、工具语义、证据驱动的下一步、数据库、引文与真实输入绑定。Learning Lens 不应获得只为它新增的宿主快捷通道。

通过后再扩展 A2A 候选审阅、组合策略和更多视图。自动评估教学效果与自动采用候选属于后续学习机制，不能用插件加载成功替代效果验证。
