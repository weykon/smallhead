# 主模型与快速选择模型：开发交接

更新：2026-10-09。状态：独立实验与 Rust calculation 方法选择链路已存在；TUI 支持运行时切换与逐任务选择。下文的通用决策契约仍是接入建议，尚未完整实现。历史性能数字来自已保存报告，本次未重新测试真实模型性能。

## 当前可体验的 TUI 链路

普通启动 `cargo run -p smallhead-tui` 即可，不要求启动时指定快速模型：

- `/route large`：默认路径，使用主模型给出的表达式。
- `/route laya` 或 `/route qwen`：后续请求的 calculation 优先调用指定服务；Agent 不覆盖手动偏好。
- `/route auto`：允许 Agent 每次 dispatch 填写 `model_choice=large_model|laya|qwen`，未填写默认沿用主模型。

discover 的 `routing_capabilities` 分别声明业务支持的后端和当前允许的选择；dispatch 校验选择后，使用程序配置的服务地址。只有 calculation 接入快速方法选择。目录声明不代表服务已启动或选择会成功。

`route_configured` 记录本轮配置，`model-route` 记录 `requested_choice`、`selection_source`、实际 `used`、后端响应及回退原因。选择失败时复用主模型已提供的表达式，无额外大模型调用。主模型仍负责理解业务与抽取参数，子 Monad 本地执行；当前实现尚未让快速模型独立理解、抽取参数或接管整个业务循环，也未证明端到端加速。切换只影响后续请求，不修改正在运行的任务。

验证覆盖 slash 切换、请求提示词和目录配置同步、逐任务调用 Laya/Qwen HTTP 接口、同一轮保留主模型路径以及禁止越过手动偏好。接口测试使用本地模拟服务，真实效果仍需启动实验服务后亲自体验。使用步骤见 [TUI README](../crates/smallhead-tui/README.md)。

## 已接入的通用能力

在计算方法单选之外，新增独立 `fast_decision` 工具，支持 Laya choice/score/noul 多问题与 Qwen rank_all/top_k/filter/select_one 策略。TUI Agent 可发现并按允许后端使用，业务代码可直接调用类型客户端。体验步骤、接口与代码走读见 [快速决策能力](fast-decision-capabilities.md)。这里的通用能力仍不等于下文所有任务版本、校准和调度契约均已实现。

## 一、架构结论

系统区分两个模型职责，不要求只有两个物理模型实例：

- 主模型／业务 Agent：理解整体目标、拆解复合任务、处理歧义、补充上下文、生成参数、综合结果。
- 快速选择服务：在短上下文和明确的有限候选中，选择或排序工具、业务入口、记忆、数据源、枚举策略；允许拒绝并返回主模型。
- 确定性运行时：构造合法候选、检查权限与有效期、验证参数、执行工具、维护状态机、处理依赖与结果。

这里的“快速”是目标角色，不是对任意小模型部署的性能保证。Laya 与 Qwen 是可替换的实验后端；不要求每次依次调用两者。

```text
当前任务与事实
  → 程序过滤候选、检查能否直接按规则决定
  → 需要有限语义选择时，提交局部决策给选择服务
  → 选择建议经过运行时校验
      → 接受：加载工具／检索内容／应用允许的枚举策略
      → 拒绝、歧义、超时、服务故障：交回主模型
  → 执行结果写入任务状态，必要时唤醒主循环
```

不必每个选择都先调用主模型生成问题，否则可能抵消延迟收益。已有结构化任务状态足够时，运行时可以直接构造选择请求；缺少必要语义时再由主模型处理。

## 二、哪些“状态、参数选择”适合交给它

| 决策 | 建议职责 |
|---|---|
| 当前问题应查订单库、规则文档还是用户记忆 | 快速模型给出来源选择建议 |
| 在本业务合法工具中选一个方法 | 快速模型选择；复合请求需要拆解或回退 |
| 已召回的记忆中哪些与任务相关 | 排序模型；项目、用户权限、失效版本先由程序过滤 |
| 从预定义回答风格、检索策略等枚举值中选择 | 可作为独立评估任务，不假设已有案例证明其准确率 |
| 订单号、金额、日期、单位等具体参数 | 解析器／主模型抽取并校验；现有两个实验未实现参数抽取 |
| 任务 running → completed、依赖是否满足、是否有权限 | 程序根据事实和事件判定，不交模型猜测 |
| 重试、并发数量、超时和资源锁 | 明确策略与调度器控制；只有确需语义判断的部分才考虑模型建议 |

区分“判断用户想做什么”和“决定系统事实上处于什么状态”。模型可以建议下一步动作，不能用相关性分数替代执行成功的证据。

## 三、已验证事实与限制

### Laya

- 独立 Python/MLX 实验；默认 127.0.0.1:3031，复用 big-head 环境与模型。
- 8 个合成案例，正常及倒序共 16 次，10/16 正确；历史报告 HTTP 中位数约 8.97ms。
- 加法选乘法、复合任务未 defer、过期偏好选择均有失败。概率高不代表业务正确。
- `selected` 已是 argmax；`No fixture result`／`execution=not_started` 表示未配置执行器或预设结果，与是否选中无关。
- 当前算术案例只有 add、multiply 等，没有 divide。除法请求选乘法说明候选缺失和拒绝能力不足；新增 divide 后仍需重新评估。
- [原始报告](../experiments/laya/baseline-2026-10-06.json)。

### Qwen3-Reranker-0.6B

- 官方权重本地服务默认 127.0.0.1:3032；MPS、FP32、逐候选评分。
- 同一组 8 个案例诊断为 7/8 正确；复合任务仍错误选择单个工具。
- 首次三候选调用约 1614ms，含预热。不能据此声称已经达到 Laya 的低延迟；需单独测量稳定及并发延迟。
- 每个候选的 yes/no 分数独立，不要求总和为 1，也不是正确率；不能与 Laya 分数直接比较或共用阈值。
- 实验中 defer 是一个额外文档，不是已经校准的拒绝机制。
- Ollama 社区转换和 top-logprobs 返回曾阻碍可靠评分，当前默认使用原生服务，见实验 README。
- [原始报告](../experiments/qwen-reranker/baseline-2026-10-06.json)。

两组报告是小样本且协议不同，不能证明某方案全面优于另一方案，也未证明通用状态／参数选择能力。目前证明的是本地调用链可运行，暴露了值得修正和评估的问题。

## 四、建议的统一契约（尚未实现）

输入包含：decision_id、task_id、task_revision、decision_kind、局部问题与必要事实、candidate_set_version、带稳定 ID 和描述的合法候选、时间预算。

输出包含：decision_id、候选 ID 或排序、backend、原始 scores、score_type、耗时；适配层给出 accept／defer 及可核查的原因，如超时、无候选、校验失败。不要伪造模型解释。

- 返回候选必须属于提交集合，任务版本必须仍有效。
- 不将两个后端原始分数统一命名为“正确置信度”。
- 接受阈值、第一二名差距等只能作为待校准策略，不能预设 0.8 或 argmax 足以可靠执行。
- 空候选、输入超长、超时、服务忙、无效输出都走明确回退；不得静默截断关键事实或无限重试。
- 新模型接口选择不等于业务执行。工具 schema、参数和执行权限另行校验。

## 五、下一步开发范围

1. 先选一个低风险任务：业务／数据源的有限候选选择。保留规则基线及现有主模型路径。
2. 在原有实验旁实现统一适配契约，保持 Laya／Qwen 可独立切换，先用模拟执行器。
3. 补充真实业务评估：中文、粤语、否定句、缺失候选、复合请求、歧义、旧记忆、候选顺序变化、长输入。
4. 将校准集与验收集分开；记录自动接受覆盖率、已接受选择的错误率、回退率、p50/p95 端到端延迟和完整任务成功率。
5. 先旁路记录建议，不改变业务行为；满足事先约定的任务指标后，再接入允许的低风险路径。

不能只优化模型推理时间：过滤、召回、模型评分、回退、工具执行的总延迟，以及错误选择带来的额外调用，都要计入。

## 给开发 agent 的任务摘要

先阅读本文和两个实验 README，核对当前运行时代码。目标是将“复杂推理”和“有限候选选择”解耦，而非用小模型接管状态机。第一轮只建立可替换的选择接口、评估与回退，避免同时扩展记忆持久化、业务并发和执行器。本文不代表已授权立即实施全部开发阶段；具体开发范围以用户交接指令为准。
